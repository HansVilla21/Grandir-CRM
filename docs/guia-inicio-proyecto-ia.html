Introducción

El problema que resuelve esta guía

La mayoría de los desarrolladores que trabajan con IA empiezan a escribir código inmediatamente. Abren Claude, pegan un requerimiento, y esperan magia. El resultado: código que no escala, contexto perdido entre sesiones, y proyectos que se vuelven imposibles de mantener.

Esta guía muestra el proceso exacto que usamos para iniciar el proyecto Grandir CRM — un sistema de gestión para un fondo de inversión costarricense con 20+ módulos, múltiples roles de usuario, y portal externo para clientes.

El proceso tiene tres etapas fundamentales:

1. Contexto global
→
2. Inicialización del proyecto
→
3. Skills + Agentes
→
4. Desarrollo iterativo

Si haces esto bien desde el inicio, Claude tendrá todo el contexto necesario para trabajar contigo como un desarrollador senior durante semanas, sin perder el hilo.

Parte 0 — Antes de abrir Claude Code

La infraestructura base

Antes de escribir una sola línea de código o hablar con Claude, necesitas tener tu infraestructura lista. Esto es lo que el cliente / tú ya deben tener configurado:

🗄️

Supabase

Crea tu proyecto en supabase.com. Conecta el MCP de Supabase en Claude Code para que el agente pueda ejecutar SQL directamente.

🚀

Vercel

Crea el proyecto en vercel.com y conecta el MCP de Vercel para deployar directamente desde Claude Code.

📁

Repositorio Git

Crea el repo en GitHub. La carpeta del proyecto ya debe existir localmente y estar abierta en VS Code.

🔑

API Keys

Ten a la mano: Supabase URL + keys, Resend API key (para emails), y cualquier otro servicio que vayas a usar.

⚠️

Importante sobre los MCPs
Los MCP tools (Supabase, Vercel) se configuran en Claude Code antes de iniciar el proyecto. Son la razón por la que Claude puede crear tablas en tu base de datos o hacer deploy sin salir del chat. Si no los tienes configurados, muchos comandos del agente no funcionarán.

Cómo conectar el MCP de Supabase

En Claude Code (VS Code extension o CLI), abre la configuración de MCPs y agrega:

// .claude/settings.json o configuración global
{
  "mcpServers": {
    "supabase": {
      "command": "npx",
      "args": ["-y", "@supabase/mcp-server-supabase@latest",
               "--supabase-url", "TU_SUPABASE_URL",
               "--supabase-key", "TU_SERVICE_ROLE_KEY"]
    }
  }
}
Parte 1 — Configuración Global

El CLAUDE.md global: tu memoria persistente

Claude Code puede leer un archivo CLAUDE.md global en ~/.claude/CLAUDE.md. Este archivo se carga en todos tus proyectos automáticamente, antes de cualquier otra cosa.

Aquí defines cómo quieres que Claude se comporte en general: idioma, reglas de seguridad, convenciones de git, comandos disponibles.

💡

Por qué importa
Sin este archivo, Claude empieza desde cero en cada sesión. Con él, tienes un asistente que ya sabe tus reglas antes de que digas una palabra.

Estructura del CLAUDE.md global

# Instrucciones Globales — Claude Code

## Comportamiento General
- Responde siempre en el mismo idioma que el usuario
- Planifica primero, ejecuta después
- Calidad sobre velocidad

## Reglas de Seguridad (Sin Excepciones)
- NUNCA escribas passwords, API keys o tokens en archivos
- NUNCA hagas commit de .env
- NUNCA hagas commit directo en main o master
- NUNCA hagas deploy a producción sin confirmación

## Reglas de Git
- Ramas: feat/, fix/, docs/, refactor/
- Mensajes de commit: tipo: descripción breve

## Comandos Disponibles
- /init-proyecto → Inicializa proyecto nuevo
- /review        → Revisa código actual
- /commit        → Commit inteligente
- /progress      → Estado del proyecto
📌

También puedes crear skills globales
En ~/.claude/skills/ puedes poner skills que estén disponibles en todos tus proyectos. Ideal para comandos como /commit o /review que uses siempre.

Parte 2 — Alimentar al Agente

Cómo darle contexto al agente de forma eficiente

Este es el paso que más diferencia a los desarrolladores que obtienen buenos resultados con IA de los que no. La calidad del output depende directamente de la calidad del input.

¿Qué documentos debe recibir Claude?

📄

Requerimientos del cliente

Documentos Word, Notion, PDFs con lo que el cliente describió. Entre más detallado, mejor. Grandir CM nos dio 20 páginas de requerimientos.

📋

Propuesta / Contrato

Lo que prometiste entregar. Define el alcance V1 y evita que Claude sobre-construya funcionalidades no solicitadas.

📐

Templates o ejemplos

Contratos, formularios, pantallas de referencia que el cliente ya usa. Claude los analiza y los refleja en el sistema.

🗺️

Wireframes o diseños

Si tienes Figma o bocetos, compártelos. Claude puede leer imágenes y entender la UI esperada antes de codear.

La forma correcta de pasarle la información

1

Abre todos los archivos en VS Code antes de hablar

Claude Code tiene acceso a todos los archivos abiertos en tu editor. Arrastra los PDFs, documentos y requerimientos al workspace antes de iniciar la conversación.

2

Dale el contexto de negocio en lenguaje natural

No solo pegues specs técnicas. Explica qué problema resuelve el sistema, quién lo usa, y por qué importa. Claude necesita entender el negocio para tomar buenas decisiones técnicas.

3

Especifica el stack tecnológico deseado

Dile exactamente qué tecnologías quieres usar. Si no lo especificas, Claude elegirá por ti — lo cual no siempre alineará con tus preferencias o lo que el cliente espera.

4

Pídele que lea, entienda, y planifique — NO que codee

El error más común: pedir código inmediatamente. El primer mensaje debe terminar con "lee esto, entiéndelo, y vamos a planificar el proyecto." Esto activa el modo de análisis, no el de ejecución.

🚫

Anti-patrón común
"Aquí está el requerimiento, créame el proyecto completo." — Esto produce código desorganizado, sin tests, sin estructura, y que no escala. Claude necesita un proceso, no solo un prompt.

Parte 3 — /init-proyecto

Inicializar el proyecto correctamente

El skill /init-proyecto crea la base del proyecto de forma estructurada. En lugar de crear archivos manualmente, le dices a Claude el nombre, propósito y tipo de proyecto, y él genera toda la estructura.

Qué genera /init-proyecto

mi-proyecto/ ├── .gitignore # Secretos, node_modules, .env ├── .env.example # Template con variables reales (sin valores) ├── CLAUDE.md # Cerebro del proyecto — reglas + contexto ├── README.md # Documentación para desarrolladores ├── .claude/ │ ├── agents/ # Agentes especializados │ └── skills/ # Skills del proyecto ├── docs/ # Specs, planes, diseños ├── memory/ # Contexto persistente entre sesiones └── src/ # Código fuente

El archivo más importante: CLAUDE.md del proyecto

Este es el archivo que Claude leerá al inicio de cada sesión. Debe contener:

Sección Qué incluir
Qué es el proyecto 2-3 oraciones del propósito del sistema
El negocio / contexto Quién lo usa, para qué, objetivos
Stack tecnológico Framework, DB, servicios, deploy
Módulos del sistema Lista de todas las funcionalidades
Cómo trabajamos Qué hacer sin preguntar vs qué requiere confirmación
Convenciones Idioma, nombres de ramas, formato de commits
Reglas específicas Restricciones propias del dominio del proyecto
✅

Resultado de hacerlo bien
Con un buen CLAUDE.md, puedes cerrar el chat, volver una semana después, y Claude tendrá todo el contexto necesario para continuar exactamente donde se quedó.

Parte 4 — Skills de Superpowers

Instalar superpowers: el framework de desarrollo

Superpowers es un conjunto de skills (habilidades) que definen cómo Claude debe abordar el desarrollo de software. No es un framework de código — es un framework de proceso.

El flujo que impone superpowers

brainstorming
→
writing-plans
→
subagent-driven
development
→
finishing-a-branch

Descripción de cada skill

Skill Cuándo usarla Qué hace
brainstorming Antes de cualquier feature nueva Hace preguntas, propone 2-3 enfoques, escribe el spec y lo guarda en docs/
writing-plans Cuando tienes el spec aprobado Crea plan de implementación con tareas de 2-5 min, código exacto, comandos
subagent-driven-development Cuando tienes el plan Despacha subagentes por tarea, revisa spec compliance y calidad de código
executing-plans Alternativa a subagent Ejecuta el plan paso a paso en la misma sesión
test-driven-development Siempre al implementar Fuerza el ciclo RED → GREEN → REFACTOR sin excepciones
systematic-debugging Ante cualquier bug Root cause analysis en 4 fases — no aplica parches sin entender la causa
using-git-worktrees Al iniciar una rama nueva Crea workspace aislado para la feature
finishing-a-development-branch Al terminar una rama Verifica tests, presenta opciones merge/PR

Instalación manual en tu proyecto

# Opción 1: Plugin oficial de Claude Code
/plugin install superpowers@claude-plugins-official

# Opción 2: Descarga manual desde GitHub
# Claude Code puede hacer esto por ti con gh CLI:
gh api repos/obra/superpowers/contents/skills/brainstorming/SKILL.md \
  --jq '.content' | base64 -d > .claude/skills/brainstorming/SKILL.md

# Repite para cada skill que necesites
💡

Tip de productividad
Puedes pedirle a Claude que descargue todas las skills en paralelo. En la demo de Grandir CRM, usamos gh api para descargar 14 skills simultáneamente en menos de 30 segundos.

Parte 5 — Agentes Especializados

Crear agentes especializados por rol

Los agentes en Claude Code son subagentes con instrucciones específicas, herramientas permitidas y contexto focalizado. En lugar de tener un solo agente que sabe todo, tienes especialistas.

Agentes creados para Grandir CRM

🎯

orquestador

Punto de entrada. Lee el contexto, decide qué agente/skill usar, coordina. Úsalo cuando no sepas por dónde empezar.

🗄️

db-architect

Solo trabaja con Supabase: schema, migraciones, RLS policies, tipos TypeScript. Tiene acceso a los MCP tools de Supabase.

⚙️

backend-dev

API routes, lógica de negocio, generación de PDFs, emails con Resend. Sigue TDD obligatorio.

🎨

frontend-dev

Dashboard interno y portal del inversionista. shadcn/ui + Tailwind. React Server Components por defecto.

🔍

code-reviewer

Solo lee, nunca modifica. Audita seguridad, calidad, tests, y cumplimiento de reglas del proyecto.

Estructura de un agente (.claude/agents/nombre.md)

---
name: db-architect
description: Diseña el schema de Supabase. Llámame cuando necesites
           crear tablas, migraciones o RLS policies.
allowed-tools: Read, Write, Edit, Bash, mcp__supabase__execute_sql
---

# Instrucciones del agente en Markdown
Eres el arquitecto de base de datos de este proyecto.
Tu especialidad es PostgreSQL + Supabase.

## Reglas
- RLS habilitado en TODAS las tablas
- Migraciones con nombres: YYYYMMDDHHMMSS_descripcion.sql
- Nunca eliminas migraciones ya aplicadas
✅

Por qué funciona esta separación
Cada agente tiene contexto reducido y focalizado. El db-architect no sabe nada de CSS, y el frontend-dev no sabe nada de migraciones. Esto reduce errores y hace que cada uno sea mejor en su área.

Parte 6 — El Desarrollo

Lo que viene después: el ciclo de desarrollo

Con la base instalada, el ciclo de desarrollo de cada feature sigue siempre el mismo patrón:

1. Brainstorming del módulo

Activas el skill brainstorming para el primer módulo (generalmente el schema de base de datos). Claude hace preguntas una a una, propone 2-3 enfoques con trade-offs, y espera tu aprobación antes de escribir cualquier código.

2. Spec document

Brainstorming genera automáticamente un documento de spec en docs/superpowers/specs/YYYY-MM-DD-nombre.md. Tú lo revisas, pides ajustes si es necesario, y apruebas. Este documento es el contrato del módulo.

3. Plan de implementación

El skill writing-plans toma el spec y crea un plan detallado con tareas de 2-5 minutos, código exacto en cada paso, y comandos para verificar que cada pieza funciona.

4. Ejecución con subagentes

subagent-driven-development despacha un subagente fresco por cada tarea del plan. Después de cada tarea: revisa spec compliance, luego calidad de código. Si algo falla, el subagente lo corrige antes de pasar a la siguiente tarea.

5. Finishing the branch

Al terminar todas las tareas, finishing-a-development-branch verifica que todos los tests pasen y presenta las opciones: merge directo, crear PR, o solicitar code review adicional.

6. Repetir por módulo

Vuelves al paso 1 con el siguiente módulo. Cada uno tiene su spec, su plan, su rama, y sus tests. El sistema crece de forma controlada y verificable.

Orden sugerido de módulos para un CRM

# Módulo Por qué primero
1 Schema de base de datos Todo lo demás depende de esto. Diseñar bien el schema evita refactors costosos.
2 Auth + Roles Sin auth, no hay seguridad. Se construye sobre el schema.
3 CRUD de entidades principales Inversionistas, contratos — el núcleo del sistema.
4 Formulario externo + Portal Las dos interfaces públicas. Requieren las entidades del paso 3.
5 Flujo de contratos (estados) La lógica más compleja. Requiere todo lo anterior.
6 Pagos y reportes Funcionalidades secundarias que dependen de contratos activos.
7 Notificaciones y comunicación Capa transversal que conecta todos los módulos anteriores.
8 Dashboard de métricas Lectura pura sobre datos existentes. Se hace al final.
Resumen

Checklist completo de inicio de proyecto

Usa esta lista antes de escribir la primera línea de código en cualquier proyecto profesional:

Antes de abrir Claude Code

  • ✓ Cuenta de Supabase creada y proyecto configurado
  • ✓ Proyecto en Vercel creado (si aplica)
  • ✓ MCPs configurados en Claude Code (Supabase, Vercel)
  • ✓ Repositorio Git creado
  • Documentos del cliente recopilados (reqs, propuesta, ejemplos)

CLAUDE.md global

  • ✓ ~/.claude/CLAUDE.md con reglas globales de comportamiento
  • ✓ Reglas de seguridad absolutas definidas
  • ✓ Convenciones de Git definidas
  • ✓ Skills globales instaladas (/commit, /review, etc.)

Inicialización del proyecto

  • /init-proyecto ejecutado (o estructura creada manualmente)
  • CLAUDE.md del proyecto con contexto completo
  • .env.example con todas las variables necesarias
  • .gitignore con .env incluido

Skills y agentes

  • Skills de superpowers instaladas en .claude/skills/
  • Agentes especializados creados en .claude/agents/
  • Spec maestra del proyecto escrita en docs/superpowers/specs/

Listo para desarrollar

  • Primer módulo en brainstorming
  • Spec aprobada por el cliente / tú mismo
  • Plan de implementación generado
  • Rama de Git creada (feat/nombre-modulo)
🎯

Si hiciste todo esto
Tienes un proyecto que puede ser trabajado por Claude durante semanas con contexto completo, por múltiples agentes especializados, con tests automatizados en cada paso, y con documentación que persiste entre sesiones. Esto es lo que diferencia un proyecto profesional de un experimento.

Caso Real

Grandir CRM — Lo que se construyó en la sesión inicial

Para contextualizar: en una sola sesión de trabajo, con este proceso, se generó toda la base de un CRM complejo para un cliente real que pagó $3,500:

📁

33 archivos creados

Estructura completa del proyecto, ninguno con código de producción aún — todo es contexto, configuración y documentación.

🤖

5 agentes especializados

Orquestador, db-architect, backend-dev, frontend-dev, y code-reviewer — cada uno con su scope definido.

⚡

14 skills instaladas

Todo el framework de superpowers descargado directamente de GitHub y personalizado para el proyecto.

📄

Spec maestra de 20 secciones

Documento de referencia completo que cubre todos los módulos, estados, flujos y reglas de negocio.

⏱️

Tiempo invertido vs beneficio
Esta sesión tomó aproximadamente 30-45 minutos. Sin esta base, cada nueva sesión de Claude requeriría re-explicar el contexto, resultando en inconsistencias y pérdida de productividad. Con la base bien puesta, cada sesión siguiente arranca en 10 segundos con contexto completo.
