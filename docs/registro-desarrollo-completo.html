4.2 Patron de Server/Client Components

Next.js App Router diferencia entre Server Components (por defecto) y Client Components ('use client'). La regla del proyecto:

  • Pages (page.tsx): Server Components - hacen fetch de datos directo con Supabase
  • Tables/Forms: Client Components - manejan estado (search, filters, modals)
  • Layout: Server Component que pasa datos como props a componentes client
  • API Routes: Server-side, manejan mutaciones con validacion
Patron clave: Los Server Components hacen el fetch y pasan datos como props a Client Components. Las mutaciones van por API Routes, no por Server Actions directamente desde el cliente (excepto auth).

5.3 Principios de Diseno de BD

Normalizado vs Denormalizado
Siempre normalizado. Tablas intermedias para N:M (contract_investors, contract_beneficiaries), emails como tabla aparte (1:N).
Porque: escalabilidad, integridad referencial, un inversionista puede tener N emails y estar en N contratos.
Token por relacion vs Token por inversionista
Token unico por par inversionista-contrato en contract_investors.portal_token.
Porque: un inversionista puede tener multiples contratos, cada portal muestra datos de UN contrato especifico.
Montos pre-calculados vs Calculados on-the-fly
Pre-calculados y almacenados (reports.calculated_amount). Los planes pueden cambiar pero los reportes historicos no.
Porque: inmutabilidad financiera. Si cambias la tasa del plan, los reportes pasados no deben cambiar.

8. Decisiones Clave de Arquitectura

Supabase RLS en todas las tablas - sin excepciones
Row Level Security habilitado en las 16 tablas con policies diferenciadas por rol (admin vs asistente). Funciones helper is_admin() e is_internal_user() como SECURITY DEFINER.
Porque: defensa en profundidad. Incluso si hay un bug en el frontend, la BD rechaza operaciones no autorizadas.
Montos de planes desde BD, nunca hardcodeados
Los planes son completamente configurables desde el dashboard. El payment_structure se almacena como JSONB.
Porque: el cliente necesita poder ajustar tasas y montos minimos sin tocar codigo. Y los contratos existentes no se afectan.
Portal por token unico vs Login del inversionista
Token unico por par inversionista-contrato. Sin cuenta de usuario para inversionistas.
Porque: simplicidad para el inversionista (no necesita recordar password), seguridad (token expirable), y el MVP no requeria login completo.
Server Components por defecto, Client Components solo cuando hay estado
Pages son Server Components que hacen fetch directo. Tablas/formularios son Client Components.
Porque: menos JavaScript en el cliente, mejor SEO, datos frescos sin cache issues. Solo se usa 'use client' cuando hay useState/useEffect.
API Routes para mutaciones vs Server Actions
Las mutaciones (crear, editar, eliminar) van por API routes. Solo auth usa Server Actions.
Porque: las API routes dan mas control (headers, status codes, error handling), son testeables, y permiten reuso desde el portal.
Audit log con JSONB diff
Cada mutacion registra old_data y new_data como JSONB. La tabla es inmutable (sin updated_at).
Porque: requisito de negocio (trazabilidad) y legal. Se puede reconstruir el estado de cualquier entidad en cualquier momento.
UI minimalista monocromatica
Paleta zinc (grises) con acentos minimos de color solo para badges de estado. Sin gradientes, sin sombras fuertes.
Porque: decision de diseno explicita del usuario. CRM profesional, no necesita color. La informacion destaca mas sobre fondo neutro.
Tipografia Montserrat
Font local (no Google Fonts CDN) para performance y privacidad.
Porque: elegancia profesional, buen soporte de caracteres latinos (tildes, enes), y carga instantanea al ser local.

10. Patrones y Convenciones

10.1 Patron de Pagina (Server Component)

// src/app/(dashboard)/dashboard/investors/page.tsx
import { createClient } from '@/lib/supabase/server'
import { InvestorsTable } from './_components/investors-table'

export default async function InvestorsPage() {
  const supabase = await createClient()

  // Fetch directo - Server Component
  const { data: investors } = await supabase
    .from('investors')
    .select('*, investor_emails(*)')
    .order('created_at', { ascending: false })

  // Pasar datos como props al Client Component
  return <InvestorsTable investors={investors ?? []} />
}

10.2 Patron de API Route

// src/app/api/investors/route.ts
import { createClient } from '@/lib/supabase/server'
import { NextResponse } from 'next/server'

export async function POST(request: Request) {
  const supabase = await createClient()

  // 1. Verificar auth
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return NextResponse.json({ error: 'No auth' }, { status: 401 })

  // 2. Validar datos
  const body = await request.json()
  if (!body.full_name) return NextResponse.json({ error: '...' }, { status: 400 })

  // 3. Operacion
  const { data, error } = await supabase.from('investors').insert({...})

  // 4. Respuesta
  if (error) return NextResponse.json({ error: error.message }, { status: 500 })
  return NextResponse.json(data, { status: 201 })
}

11. Seguridad

Capas de Seguridad

  1. Supabase Auth: JWT tokens, sesion segura via cookies HttpOnly
  2. Middleware Next.js: Redirige a login si no hay sesion valida
  3. RLS PostgreSQL: Cada query filtrada por rol del usuario autenticado
  4. API Validation: Cada endpoint valida auth + datos de entrada
  5. Portal Tokens: Tokens unicos, expirables, solo lectura + acciones especificas
  6. Storage Policies: Solo usuarios autenticados pueden leer/escribir archivos
  7. .env nunca en git: Variables de entorno en Vercel, .env.example con placeholders
Reglas absolutas del proyecto:
  • NUNCA hardcodear API keys, tokens o secretos en ningun archivo
  • NUNCA hacer commit de .env
  • NUNCA commit directo a main
  • NUNCA deploy a produccion sin confirmacion explicita

13. Sistema de Agentes IA

El proyecto usa el framework "Superpowers" de Claude Code - un sistema de agentes especializados y skills que orquestan el desarrollo.

13.1 Como funcionan los Agentes

Cada agente es un archivo Markdown en .claude/agents/ que define:

  • Rol: Que hace este agente
  • Herramientas: Que tools puede usar
  • Restricciones: Que NO puede hacer
  • Contexto: Que archivos debe leer primero (siempre CLAUDE.md)

El orquestador recibe la tarea del usuario, lee el contexto, y delega a agentes especializados que trabajan en paralelo.

13.2 Ejemplo: Responsive con 4 Subagentes

Para el overhaul responsive (~40 archivos), se lanzaron 4 subagentes frontend-dev en paralelo:

  1. Agente 1: Inversionistas (page, table, form, detail, toggle)
  2. Agente 2: Contratos (page, table, form, detail, actions, payments)
  3. Agente 3: Pagos (page, table, form, verify)
  4. Agente 4: Reportes + Boletines (pages, tables, forms, detail)

Mientras los subagentes trabajaban, el desarrollador principal actualizo manualmente: referidos, notificaciones, settings, help, portal, login.

Resultado: ~40 archivos actualizados simultaneamente con patrones consistentes.

13.3 Skills como "Recetas"

Los skills en .claude/skills/ son plantillas reutilizables:

  • /brainstorming — Antes de cualquier feature nueva
  • /writing-plans — Plan detallado antes de codear
  • /commit — Commit con formato convencional y revision de secretos
  • /review — Revision contra reglas del CLAUDE.md
  • /security-check — Escaneo de secretos y configuracion

14. Lecciones Aprendidas

Sobre Desarrollo con IA

  • CLAUDE.md es critico: El archivo de instrucciones del proyecto es lo que hace que la IA mantenga coherencia entre sesiones. Sin el, cada conversacion empieza de cero.
  • Specs antes de codigo: Invertir tiempo en la especificacion maestra ahorro horas de reescritura. La IA sigue el spec al pie de la letra.
  • Subagentes para paralelismo: 4 agentes trabajando en paralelo es 4x mas rapido, pero requiere patrones claros para mantener consistencia.
  • Verificar siempre: Despues de cada cambio significativo, correr npx next build. Los errores de tipo se acumulan si no se verifican.
  • Memoria explicita: Las decisiones de diseno se guardan en archivos de memoria para que conversaciones futuras no las contradigan.

Sobre Arquitectura

  • RLS desde el dia 1: Agregar seguridad despues es 10x mas dificil. Supabase RLS desde la primera migracion.
  • Normalizar siempre: La tentacion de poner emails como array en investors fue grande. La tabla separada permitio multiples emails con estado individual.
  • JSONB para configuracion flexible: payment_structure como JSONB permite agregar nuevos tipos de planes sin migrar la BD.
  • Audit log inmutable: old_data/new_data como JSONB. Reconstruir el historial de cualquier entidad es trivial.

Sobre Responsive

  • Mobile-first real: Empezar sin clases responsive, agregar sm:/lg: para pantallas mas grandes.
  • Nunca margenes negativos en cards: -mx-4 dentro de contenedores con border causa overflow invisible que rompe todo el layout.
  • Breakpoints vs sidebar: Si hay sidebar en lg (1024px - 240px = 784px), los grids de 4 columnas no caben. Usar xl.
  • Regla permanente: Todo componente nuevo DEBE ser responsive. Agregada al CLAUDE.md como regla #7.

Sobre el Proceso

  • Un task, un chat: Mezclar temas en una sola conversacion genera confusiones.
  • Confirmar antes de deploy: Nunca hacer deploy automatico. Siempre verificar build local primero.
  • Errors como oportunidad: Cada error encontrado en produccion se convierte en una regla en CLAUDE.md para que no se repita.
